# Security and Responsible-AI Review

## Security boundary

The supported deployment is a trusted, single-user Cognizant Windows laptop.
The service binds to `127.0.0.1`, uses synthetic data, and makes no runtime
network calls. It is not approved for production, shared-host, internet-facing,
or real client-data use.

## Threats considered

| Threat | Risk in this MVP | Mitigation or disposition |
|---|---|---|
| Hardcoded credentials | Secret disclosure | No credentials or model API required; secret patterns reviewed |
| Sensitive-data logging | Requirement or filesystem disclosure | Generic failures log correlation and exception type only |
| Empty, malformed, or oversized input | Invalid state or resource consumption | Pydantic types, trimming, required fields, and length limits |
| SQL injection | Database manipulation | Parameterized SQLite statements |
| Script/content injection | Browser code execution | Jinja2 escaping and DOM `textContent`; no `innerHTML` or `eval` |
| Path traversal or unsafe file access | Local file disclosure/modification | HTTP input does not select filesystem paths |
| Approval bypass | Unauthorized downstream generation | Server-side state machine and approval guards |
| Duplicate/replayed input | Duplicate artifacts | Normalized SHA-256 requirement hash; other mutations are state-guarded |
| Excessive error disclosure | Internal implementation leakage | Standard sanitized error envelopes with request IDs |
| Cross-origin access | Browser-origin abuse | No permissive CORS middleware |
| Cross-site request forgery | Unauthorized local browser mutation | Remaining risk; local-only boundary and no authentication |
| Unauthenticated destructive actions | Project mutation by local callers | Remaining risk; no delete/release/deployment endpoints exist |
| Dependency vulnerability | Package compromise | Pinned versions, `pip check`, and local `pip-audit` |
| Archive/build-context leakage | Shipping secrets, data, or environments | `.gitignore` and `.dockerignore` exclusions |
| Fabricated knowledge | Misleading generated artifacts | No external knowledge retrieval; assumptions are explicit |
| Unsafe generated content | Invalid or misleading downstream use | Typed models and pre-persistence domain validation |

## Implemented security controls

- Loopback binding by default
- No runtime outbound calls, credentials, tokens, or paid APIs
- Pydantic validation and maximum lengths on API fields
- Empty requirement and rejection-reason rejection
- Parameterized SQL with explicit transactions and rollback
- Standard response/error envelopes and request correlation IDs
- Sanitized unexpected errors without response stack traces
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- Jinja2 escaping and `textContent` for generated browser content
- Server-side transition and approval enforcement
- Append-only approval and audit records by application behavior
- Duplicate requirement detection
- Pinned dependencies and source/build exclusion rules

## Responsible-AI controls

- Every generated artifact identifies deterministic rules and a rules version.
- The product never claims deterministic templates were generated by an LLM.
- Assumptions, ambiguities, and unresolved risks remain visible.
- Generated artifacts retain source requirement and approval traceability.
- Validation failure prevents persistence and downstream processing.
- Human approval is mandatory before backlog and test generation.
- The system does not invent or claim previous-project knowledge.
- Planned agents are labelled Planned or Partial and are not executable.
- No deployment, release, Git, Jira, or external action occurs automatically.
- A future runtime LLM requires separate provider, data, prompt-injection,
  structured-output, and authorization review.

## Synthetic-data statement

Only synthetic hackathon data is permitted. Do not enter:

- Client or proprietary requirements
- Personal or health information
- Credentials, secrets, or access tokens
- Real financial or production records
- Confidential standards, source code, or internal decisions

The checked-in sample dataset contains twenty invented feature requirements and
an explicit synthetic-data notice.

## Verification evidence

Phase 4 and Phase 5 checks included:

- Automated malformed, empty, oversized, duplicate, SQL-like, script-like, and
  traversal-like input cases
- Approval barrier, invalid transition, rejection, and controlled repository
  failure tests
- Static searches for hardcoded credentials, dangerous rendering, dynamic code
  execution, shell execution, unsafe file access, and permissive CORS
- `pip check`
- Local `pip-audit`; after upgrading project-local pip to 26.1.2, no known
  vulnerabilities were reported
- 29 passing tests with 97.11% line coverage

Confirmed defects corrected during review:

1. Generic exception logging previously retained full exception text and a
   traceback. It now records only correlation ID and exception type.
2. QA generation originally lacked required negative and boundary tests. Rules
   and validation now enforce all three test types per acceptance criterion.
3. Frontend dynamic content and agent details were checked to use safe DOM
   insertion rather than raw HTML.

## Remaining risks

- No authentication, authorization, or verified reviewer identity
- No CSRF tokens or rate limiting
- No global body limiter outside schema field limits
- No general idempotency-key mechanism
- SQLite is unencrypted at rest
- Audit records are not cryptographically tamper-evident
- Single-user design; concurrent writers and database corruption recovery are
  not tested
- Dependency licenses have not been formally reviewed
- Docker execution was unavailable in the verified environment
- Interactive browser, keyboard, screen-reader, and visual-regression testing
  remain incomplete despite responsive DOM/CSS contract checks

These risks are acceptable only within the stated local synthetic-data
hackathon boundary. They block production or shared deployment.
